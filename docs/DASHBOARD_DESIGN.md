# Local activity dashboard — architecture decision

**Status:** accepted for subsequent implementation planning after independent review for [#3](https://github.com/dimchansky/terminal-mcp/issues/3), 2026-10-28. **Parent:** [#2](https://github.com/dimchansky/terminal-mcp/issues/2). This document chooses the approach and the minimum shared contracts; it does **not** describe implemented dashboard functionality. The parent issue and [AGENTS.md](../AGENTS.md) remain authoritative for security, complete input audit and fail-closed behavior.

## 1. Evidence and observation limits

Checked against source `main` `21b88f6` and the separately installed HTTP server revision `b7d9340`. The installed server's audit was inspected **read-only**, using anonymized aggregates. No raw request arguments, token, user identifier, conversation ID, location or complete journal record is copied here.

| Source or question | Observed evidence | Safe claim |
| --- | --- | --- |
| ChatGPT-originated MCP calls | `request_start.call_meta` often contains `openai/session` and `io.modelcontextprotocol/clientInfo`; some historical calls have no metadata ([middleware](../internal/mcpserver/audit_requests.go#L36-L68)). | An opaque, **client-claimed** conversation hint may be available, but is not mandatory or authenticated. |
| Across messages/restarts | Five known calls matched by **our own unique test operation IDs and call times** in this ChatGPT conversation, across separate user turns, two dates and two server instances, shared one opaque `openai/session` value. Several other opaque IDs also span server instances. | Stability has been **observed**, not guaranteed by all clients or future versions. |
| **Different ChatGPT chat windows** | Historical journal has distinct hints but no independently verified mapping from each hint to an actual browser chat window. | **Not independently verified.** When available, the owner may invoke read-only `terminal_list` in two separate turns of one chat (with page reload) and a second chat; compare only equal/different/absent locally. Until then, never promise that every distinct chat has a distinct hint. |
| Claude, Codex or other hosts | No independently verified calls from these clients through this server in the inspected sample. | **Untested**; without a per-conversation hint, show unattributed actions, optionally filtered by claimed client name. |
| Local HTTP vs embedded tunnel | Both reach the same authenticated `/mcp` and tool middleware; `tunnelRoundTripper` replaces Authorization and pins the URL ([source](../cmd/terminal-mcp/tunnel.go#L145-L169)). | Existing audit has **no trusted per-request ingress marker**; do not label an action “remote” or “local” based on `_meta`. |
| Process completion and file changes | `terminal_start` records process submission, not autonomous child exit; read/observation calls can record later status. An arbitrary shell command may modify unobserved files ([SPEC](../SPEC.md#L541-L550)). | Do not invent process exits, full filesystem diffs or complete chat transcripts. |

**Identity policy:** `ConversationKey = (metadata field namespace, opaque value)` is strictly an **unverified session-hint grouping key**, not a validated chat identity, e.g. `("openai/session", value)`, where the value is present and nonempty. Do **not** include `server_id`, `clientInfo` name/version or `openai/subject` in the key: they are different concepts, and the latter are unverified client annotations. Missing or invalid hints mean **unattributed** actions, not a fabricated chat session. Multiple unattributed calls can appear under a common visual filter but must not be treated as one conversation. Short displayed IDs and deterministic identicons are **visual hints, not proof of uniqueness or authenticity**; lengthen truncated IDs on collision, retain text alongside any icon and allow an optional owner alias. **If a later two-chat check finds the same hint in unrelated chats, label it as a claimed session-hint lane and do not present it as a one-to-one chat identity; reassess the UX contract before implementing chat-specific claims.** A holder of the powerful MCP bearer could forge the hint. A trusted ingress signal would require an explicit future design and audit change, not covert inference.

## 2. Chosen topology

**Decision: A — embed the viewer as separately guarded routes on the existing local HTTP listener.** Do not add a second listener, second daemon, database or dedicated audit-log broker for the MVP.

| Alternative | Benefit | Why not selected |
| --- | --- | --- |
| **A — shared listener/Go process** (chosen) | Direct access to audit's future confirmed-append boundary, no extra process/port/configuration, same installed lifecycle. | Must dispatch viewer routes to a **different guard** before the current catch-all wrapper, keeping `/mcp`/admin behavior unchanged; use response-local write deadlines and cancel viewer connections before normal unbounded HTTP shutdown. The browser never receives the MCP bearer, so even script compromise in viewer origin must not authorize `/mcp`. These are focused router/viewer lifecycle changes, not a broad guard relaxation. |
| **A′ — separate listener in the same process** | Independent viewer origin and HTTP deadlines; viewer HTTP server can be closed separately, with the same in-process audit. It could bind an **ephemeral** loopback port and return its URL from a local pairing endpoint. | Still needs another listener/serve/stop/error path and URL discovery; ephemeral origin changes on restart, losing origin-local aliases/preferences, while a fixed port needs collision handling. Viewer tokens, protection from hostile scripts, stream backpressure and safe shutdown still need design. The extra origin is useful defense-in-depth but not necessary with a separate read-only credential and strict MCP guard. |
| **B — separate viewer process** | Can stay alive through MCP restarts and could browse offline history. | Does not avoid modifying the MCP server: an external reader cannot treat physical EOF as a committed boundary after a failed append/repair. It also needs authenticated frontier/notification IPC, process lifecycle and another port. Offline history viewing is not an MVP goal. |

The currently private audit `Log` serializes confirmed appends but **does not yet expose a viewer cursor or wake-up** ([writer](../internal/audit/audit.go#L181-L242)). Issue [#4](https://github.com/dimchansky/terminal-mcp/issues/4) adds those in one change; this ADR does not claim they already exist.

**Feasibility:** isolated Go `net/http` trials (no production listener touched) showed response-local `http.ResponseController.SetWriteDeadline` allows streaming beyond an otherwise failing server-wide `WriteTimeout`. A real SSE handler immediately flushing events also remained active for **7 seconds with `ReadTimeout: 2s`** both with and without explicit clearing of its read deadline; an idle header-only test would not have been sufficient. A separate **70-second** test on **Go 1.27.3** with the production HTTP settings (`ReadHeaderTimeout: 5s`, `ReadTimeout: 15s`, `WriteTimeout: 30s`, `IdleTimeout: 60s`) delivered all 14 SSE heartbeats at 5-second intervals **without resetting the read deadline**; the handler completed normally. This validates feasibility for this Go runtime, while #8 must still test slow/non-reading clients and long viewer sessions. Each viewer write still needs a **finite** write deadline, so a stalled receiver cannot block service shutdown. #8/#10 must regression-test a long stream whose context survives the server's read/idle deadlines, plus a non-reading client whose blocked writes terminate on the per-write deadline. A separate viewer cancellation/fence is needed whichever in-process topology is chosen. Existing `/mcp` limits and the unbounded production drain remain unchanged ([serve](../cmd/terminal-mcp/main.go#L348-L423)). The one-port solution also preserves stable browser-origin aliases and avoids a second listener/configuration/startup failure path; **this**, rather than an alleged inability to use ephemeral ports, is why A is preferred to A′.

**Topology consequence:** existing subissue boundaries **stay valid**. In particular, #4 owns both confirmed-frontier publication and the nonblocking post-commit wake-up; #8 consumes them without revisiting audit-writer internals.

## 3. Minimum semantic contract, not a wire schema

- **Record identity and ordering:** `RecordPos` is an opaque, equality-comparable identifier for one journal record that survives rotation/rename. Reader #4 defines its internal segment/offset/fingerprint encoding; reducer #5 must **not import the reader**. `Cursor` is an opaque validated checkpoint **after** a complete OS-acknowledged append. It survives reconnects when history is intact. Position, not the event's pre-append timestamp, establishes journal order. Missing/truncated/repaired/replaced history or any segment that cannot be authenticated by its recorded fingerprint/record boundary produces an explicit `gap` / `resync`, never silent continuity.
- **Source of truth:** one existing JSONL audit with numbered archives. A successful append advances an acknowledged frontier; a coalesced notification only wakes a reader **after** success. Physical EOF or a visible newline after a failed append is not evidence of admission. A crash/power loss may make prior completion unknowable; never fabricate certainty. Viewer reads never take the audit writer lock, perform recovery, alter the journal or hinder Windows rotation: a Windows handle without `FILE_SHARE_DELETE` can make writer rename fail and consequently deny pre-effect MCP work. #4 owns the native Windows share/delete and concurrent-rotation proof.
- **Action correlation:** `RequestKey = (server_id, request_id)` identifies a specific MCP call. `EffectKey = (server_id, operation_id)` identifies the newly admitted effect; a retry gets a new request, not a second effect. The effect belongs to its original admitted request even if another chat replays it. `session_id` means a **managed terminal process**, not an AI chat. `request_finish` is not interchangeable with `operation_finish`, and process exit is known only through later recorded observations.
- **Bounded projection:** a small `ActivitySummary` exposes source hint/confidence, stable request/effect references, tool, phase/status, ordering/time, replay and unknown flags, and a bounded human-readable command/file hint. It does **not** stream full private inputs. A separately requested detail lookup, authorized **on every call using the same scoped viewer token** (not a second credential), reveals the **complete** original raw tool arguments on demand. Responses must include `Cache-Control: no-store` and strict output escaping. A finish whose `request_start` is beyond the loaded window is `origin_not_loaded`, not “unattributed”; #5 handles late-origin reattribution and idempotent replay, while #7 owns bounded historical lookup. In-flight effects from the current server instance are retained until real completion.
- **Snapshot → live:** authenticated bounded history returns `coverage` and a **resume cursor at the acknowledged frontier**. The stream begins *after* that cursor, delivering at least once; consumers deduplicate using `RecordPos`. On invalidated history, rebuild from a fresh bounded snapshot and show a gap. Stream delivery does not participate in admission or fail-closed audit decisions.
- **Unavailable data:** audit disabled or damaged is an explicit viewer status, not an empty “complete” history. No inference of actual model, chat title, chat creation/closure, trusted ingress or indirect filesystem mutation. Any live process-state overlay would be clearly *volatile* and is **not** added to the MVP without separate scope.

These are behavioral boundaries only. The owning issues select the Go types, exact JSON fields, routing names, cursor encoding and implementation techniques, subject to [#2](https://github.com/dimchansky/terminal-mcp/issues/2).

## 4. Owner entry, security and service lifecycle

**MVP entry:** HTTP-mode server only, using the **existing canonical literal loopback host and port** (normally `127.0.0.1:8090`). Add an explicit `terminal-mcp dashboard` convenience action: for a **standalone `start`** instance, use its existing saved local listener and protected token-file configuration ([controller](../cmd/terminal-mcp/standalone.go#L22-L85), [control](../cmd/terminal-mcp/standalone.go#L380-L425)). An independently launched foreground `serve` instance has no guaranteed discoverable saved config: require an explicit target address and token-file path (or a safely inherited existing token environment) for the CLI action; missing/disconnected service returns a clear error. The stdio transport has no web viewer. No auto-launch or external network exposure is implied.

**Authentication:** the CLI proves ownership using the existing local full-power bearer **outside the browser**, obtains a short-lived, unguessable, single-use *viewer-only* pairing code and opens a **grant-free** local login URL. For the initial MVP, the code can be displayed in the private terminal for manual paste; this friction is intentional until an equally safe flow is demonstrated. **Neither bearer nor pairing code appears in browser argv, URL, referrer or persistent storage.** After exchange, the browser holds a separate **read-only**, expiring viewer token in per-tab `sessionStorage` (page reload keeps it; a new independent tab needs login) and sends it as a header for every history/detail/live request. SSE-format delivery uses authenticated `fetch`, not cookie-only `EventSource`. Viewer credentials never authorize `/mcp`, maintenance or file/process mutation.

**Access boundary:** viewer routes have their own strict exact Host/Origin/Fetch-Metadata and header guard; do not relax `httpguard.Wrap`'s restrictions on `/mcp` and existing admin routes ([guard](../internal/httpguard/guard.go#L69-L105)). A tightly enumerated local-admin pairing operation uses full bearer; access to it over the embedded tunnel must remain impossible. The tunnel currently forwards **only** exact `/mcp` ([source](../cmd/terminal-mcp/tunnel.go#L153-L169)). The transport's existing ability to execute commands/read files means remote agents trusted with the MCP bearer may already read the audit: viewer-route isolation is not a new sandbox or user identity boundary. **A read-only viewer credential is still highly sensitive:** it grants access to complete audit inputs, which may include passwords, tokens, signed URLs and source code. Require a strict CSP without inline/eval or third-party scripts, render untrusted tool text through text nodes (no HTML interpretation), and avoid external assets, telemetry and exposing raw inputs in browser logs. Keep limits on login attempts, grants, viewers, live streams and detail reads.

**Lifetimes and stopping:** choose bounded rolling viewer expiry with a separate absolute maximum. Viewer pairing, login and read-only routes are **independent of the MCP mutation admission gate**; they remain available during draining subject to viewer authorization/resource limits, and are rejected at the final viewer fence. Permit **new pairing and renewal during a long graceful drain**, subject to the same strict authentication and resource caps: read-only viewing is not a new mutation, and the owner may need to open the dashboard specifically to see what is delaying shutdown. One shared shutdown point, immediately **before `httpServer.Shutdown`** in `serveHTTPWithOptions`, must atomically fence new viewer requests, send a best-effort viewer-only `server_stopping` signal, cancel existing viewer handlers and then invoke the existing **unbounded** production HTTP shutdown. On the **normal `ctx.Done` → `Shutdown` path** this point follows the appropriate mode-specific preparations: `TryFinishDrain` for ordinary stop and externally coordinated freeze for update. Force may abort effects and need not await a viewer; **every alternative exit** (including unexpected `Serve` failure or forced close) must either fence/cancel viewers or close their connections directly. Do not claim all effects completed on force. It must cover SIGINT/SIGTERM, maintenance stop/update and force, without allowing viewer handlers to delay MCP. This timing is an approximation of live coverage, **not a promise that every audit event was streamed**: `TryFinishDrain` waits for mutations/sessions but not necessarily every read-only HTTP request, whose `request_finish` may be written during HTTP shutdown and remain available only via replay ([manager](../internal/session/manager.go#L389-L450), [HTTP shutdown](../cmd/terminal-mcp/main.go#L387-L422)). #6 owns the viewer fence/cancel primitive; #8 calls it once at this common shutdown boundary. An operator invoking `terminal-mcp dashboard` during an update freeze may still authenticate against the **old** live instance until the final fence; after activation/restart its viewer tokens are invalid. Show a re-login state, not endless reconnection.

**UX tradeoffs accepted:** one port, one process and a simple CLI-assisted login outweigh automatic new-tab sign-in and surviving service updates without login. Exact TTLs, endpoint paths and session-store implementation belong to #6; they must realize the safety and continuity policy above.

## 5. Minimal desktop UX sketch

Fictional data; icons stand for optional locally derived deterministic identicons. Never send an actual chat ID to an external image service.

```text
LOCAL ACTIVITY                                   ● Live | Audit writes healthy

Observed sources                Activity / chosen source           Details
▣ Claimed OpenAI · 7fa2…         10:32 terminal_start · submitted   argv / cwd
  alias: Build work             10:32 terminal_read  · observed    full supplied input
▧ Claimed OpenAI · 41c9…         10:33 file_edit      · applied     requested changes
  last observed: 10:33         10:34 file_receive   · no finish  outcome not yet recorded
◇ Unattributed · client claimed  10:35 replay         · no effect  original request

[Earlier history]   [Filter tool/status]   [Pause]   [Reconnect]
```

A deterministic icon can help locate a conversation at a glance, but a collision-safe short text ID/optional alias must remain. Client-claimed labels are explicitly marked as such; abbreviated command/file summaries visibly indicate truncation. The audit journal **does not** store live download progress (an eventual `operation_finish` receipt is different), so no real-time progress is claimed here. Repeated `terminal_read` / `file_receive_result` polls collapse into one readable action without hiding raw events in detail. Show distinct states: live, reconnecting, coverage gap, audit disabled, draining/stopping, unauthenticated/expired, origin outside the loaded window. Completion of an MCP request, completion of its mutation and later observed child exit are never presented as the same event.

**MVP:** recognizable sources, accurate recent request/effect activity, live changes, bounded replay, full raw input detail on demand, safe local authentication. **Defer:** chat transcripts/names/models, complete subprocess output, implicit file diffs, broad full-text search/analytics, remote dashboard, visual theming and mobile-specific polish.
