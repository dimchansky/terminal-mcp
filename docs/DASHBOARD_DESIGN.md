# Local activity dashboard — architecture decision

**Status:** accepted for subsequent implementation planning after independent review for [#3](https://github.com/dimchansky/terminal-mcp/issues/3), 2026-10-28. **Parent:** [#2](https://github.com/dimchansky/terminal-mcp/issues/2). This document chooses the approach and the minimum shared contracts; it does **not** describe implemented dashboard functionality. The parent issue and [AGENTS.md](../AGENTS.md) remain authoritative for security, complete input audit and fail-closed behavior.

## 1. Evidence and observation limits

Checked against source `main` `21b88f6` and the separately installed HTTP server revision `b7d9340`. The installed server's audit was inspected **read-only**, using anonymized aggregates. No raw request arguments, token, user identifier, conversation ID, location or complete journal record is copied here.

| Source or question | Observed evidence | Safe claim |
| --- | --- | --- |
| ChatGPT-originated MCP calls | `request_start.call_meta` often contains `openai/session` and `io.modelcontextprotocol/clientInfo`; some historical calls have no metadata ([middleware](../internal/mcpserver/audit_requests.go#L36-L68)). | An opaque, **client-claimed** conversation hint may be available, but is not mandatory or authenticated. |
| Across messages/restarts | Five known calls matched by **our own unique test operation IDs and call times** in this ChatGPT conversation, across separate user turns, two dates and two server instances, shared one opaque `openai/session` value. Several other opaque IDs also span server instances. | Stability has been **observed**, not guaranteed by all clients or future versions. |
| **Different ChatGPT chat windows** | Historical journal has distinct hints but no independently verified mapping from each hint to an actual browser chat window. | **Not independently verified.** When available, the owner may invoke read-only `terminal_list` in two separate turns of one chat (with page reload) and a second chat; compare only equal/different/absent locally. Until then, never promise that every distinct chat has a distinct hint. |
| Claude, Codex or other hosts | No independently verified calls from these clients through this server in the inspected sample. | **Untested**; without a per-conversation hint, show unattributed actions, optionally filtered by claimed client name. |
| Local HTTP vs embedded tunnel | Both reach the same authenticated `/mcp` and tool middleware; `tunnelRoundTripper` replaces Authorization and pins the URL ([source](../cmd/terminal-mcp/tunnel.go#L145-L169)). | Existing audit has **no trusted per-request ingress marker**; do not label an action “remote” or “local” based on `_meta`. |
| Process completion and file changes | `terminal_start` records process submission, not autonomous child exit; read/observation calls can record later status. An arbitrary shell command may modify unobserved files ([SPEC](../SPEC.md#L541-L550)). | Do not invent process exits, full filesystem diffs or complete chat transcripts. |

**Identity policy:** `ConversationKey = (metadata field namespace, opaque value)` is strictly an **unverified session-hint grouping key**, not a validated chat identity, e.g. `("openai/session", value)`, where the value is present and nonempty. Do **not** include `server_id`, `clientInfo` name/version or `openai/subject` in the key: they are different concepts, and the latter are unverified client annotations. Missing or invalid hints mean **unattributed** actions, not a fabricated chat session. Multiple unattributed calls can appear under a common visual filter but must not be treated as one conversation. Short displayed IDs and deterministic identicons are **visual hints, not proof of uniqueness or authenticity**; lengthen truncated IDs on collision, retain text alongside any icon and allow an optional owner alias. **If a later two-chat check finds the same hint in unrelated chats, label it as a claimed session-hint lane and do not present it as a one-to-one chat identity; reassess the UX contract before implementing chat-specific claims.** A holder of the powerful MCP bearer could forge the hint. A trusted ingress signal would require an explicit future design and audit change, not covert inference.

## 2. Chosen topology

**Decision: A — embed the viewer as separately guarded routes on the existing local HTTP listener.** Do not add a second listener, second daemon, database or dedicated audit-log broker for the MVP.

| Alternative | Benefit | Why not selected |
| --- | --- | --- |
| **A — shared listener/Go process** (chosen) | Direct access to audit's future confirmed-append boundary, no extra process/port/configuration, same installed lifecycle. | Must dispatch viewer routes to a **different guard** before the current catch-all wrapper, keeping `/mcp`/admin behavior unchanged; use response-local write deadlines and cancel viewer connections before normal unbounded HTTP shutdown. The browser never receives the MCP bearer, so even script compromise in viewer origin must not authorize `/mcp`. These are focused router/viewer lifecycle changes, not a broad guard relaxation. |
| **A′ — separate listener in the same process** | Independent viewer origin and HTTP deadlines; viewer HTTP server can be closed separately, with the same in-process audit. It could bind an **ephemeral** loopback port and return its URL from a local pairing endpoint. | Still needs another listener/serve/stop/error path and URL discovery; ephemeral origin changes on restart, losing origin-local aliases/preferences, while a fixed port needs collision handling. Viewer tokens, protection from hostile scripts, stream backpressure and safe shutdown still need design. The extra origin is useful defense-in-depth but not necessary with a separate read-only credential and strict MCP guard. |
| **B — separate viewer process** | Can stay alive through MCP restarts and could browse offline history. | Does not avoid modifying the MCP server: an external reader cannot treat physical EOF as a committed boundary after a failed append/repair. It also needs authenticated frontier/notification IPC, process lifecycle and another port. Offline history viewing is not an MVP goal. |

The private audit `Log` now exposes its acknowledged frontier and coalesced wake-up through the internal reader implemented by [#4](https://github.com/dimchansky/terminal-mcp/issues/4). It does **not** expose any public dashboard, viewer HTTP route, or viewer authentication. The shared-listener decision is unchanged.

**Feasibility:** isolated Go `net/http` trials (no production listener touched) showed response-local `http.ResponseController.SetWriteDeadline` allows streaming beyond an otherwise failing server-wide `WriteTimeout`. A real SSE handler immediately flushing events also remained active for **7 seconds with `ReadTimeout: 2s`** both with and without explicit clearing of its read deadline; an idle header-only test would not have been sufficient. A separate **70-second** test on **Go 1.27.3** with the production HTTP settings (`ReadHeaderTimeout: 5s`, `ReadTimeout: 15s`, `WriteTimeout: 30s`, `IdleTimeout: 60s`) delivered all 14 SSE heartbeats at 5-second intervals **without resetting the read deadline**; the handler completed normally. This validates feasibility for this Go runtime, while #8 must still test slow/non-reading clients and long viewer sessions. Each viewer write still needs a **finite** write deadline, so a stalled receiver cannot block service shutdown. #8/#10 must regression-test a long stream whose context survives the server's read/idle deadlines, plus a non-reading client whose blocked writes terminate on the per-write deadline. A separate viewer cancellation/fence is needed whichever in-process topology is chosen. Existing `/mcp` limits and the unbounded production drain remain unchanged ([serve](../cmd/terminal-mcp/main.go#L348-L423)). The one-port solution also preserves stable browser-origin aliases and avoids a second listener/configuration/startup failure path; **this**, rather than an alleged inability to use ephemeral ports, is why A is preferred to A′.

**Topology consequence:** existing subissue boundaries **stay valid**. In particular, #4 owns both confirmed-frontier publication and the nonblocking post-commit wake-up; #8 consumes them without revisiting audit-writer internals.

## 3. Minimum semantic contract, not a wire schema

**Normalized identity fields (fixed API names):** the reducer (#5) produces the following source-identity object for use by history/live APIs (#7/#8) and the UI (#9). The example values are illustrative, **not hashed or generated IDs**:

```json
{
  "clientName": "openai-mcp",
  "conversationId": "c7e42ab19d...",
  "identitySource": "openai/session",
  "identityVerified": false
}
```

- `clientName`: the original name supplied by `call_meta["io.modelcontextprotocol/clientInfo"].name`, or `null` if absent; this name is **client-claimed**, not trusted.
- `conversationId`: the **unchanged, full string value** from a recognized per-conversation metadata field, or `null` if missing/invalid. No hashing, truncation or synthetic fallback; preserve enough information to recover the original identifier.
- `identitySource`: the **exact original metadata field name** used for `conversationId` (for example `"openai/session"`), or `null` when there is no conversation ID. The pair `(identitySource, conversationId)` is the grouping key, not `conversationId` alone.
- `identityVerified`: `false` for all current client-supplied metadata; never infer verification from the client name, bearer, tool-call ID, or repeat frequency. A future `true` requires an explicitly established trusted server-side verification mechanism.

For example, if a client identifies itself only as `claude-code` without a conversation hint, the object contains `"clientName": "claude-code"`, `"conversationId": null`, `"identitySource": null`, and `"identityVerified": false`. A missing client name is also `null`, not a fabricated name. Normalization is a **read-only projection**: preserve original `call_meta` in the audit; new providers may later map their documented per-conversation fields into these same four fields, without changing the UI contract. Per-tool IDs, request IDs, and terminal process session IDs are **not** substitutes for conversation IDs. Identicon generation and short visible labels belong to the UI and must not replace the original API values.

- **Record identity and ordering:** `RecordPos` is an opaque, equality-comparable byte-derived position that survives normal rotation/rename, **not a globally unique event ID**: distinct archives with identical first-line bytes and identical target-record bytes at the same offset can collide. Reader #4 defines its internal segment/offset/fingerprint encoding; reducer #5 must **not import the reader** and must retain source/ordering context to distinguish such occurrences. `Cursor` is an opaque validated checkpoint at a complete record boundary, either within the current writer's observed historical baseline or after a complete OS-acknowledged append. Historical boundaries do not establish earlier admission or acknowledgement. The cursor survives reconnects when history is intact. Position, not the event's pre-append timestamp, establishes journal order. Detected loss or alteration of a source referenced by a cursor or a current writer observation produces explicit `gap` / `resync`. Removing an unreferenced preexisting archive may be undetectable after fresh inventory; missing suffix numbers alone prove neither deletion nor continuity. Byte-derived proofs are not tamper-proof authentication.
- **Source of truth:** one existing JSONL audit with numbered archives. A successful append advances an acknowledged frontier; a coalesced notification only wakes a reader **after** success. Physical EOF or a visible newline after a failed append is not evidence of admission. A crash/power loss may make prior completion unknowable; never fabricate certainty. Viewer reads never take the audit writer lock, perform recovery, alter the journal or hinder Windows rotation: a Windows handle without `FILE_SHARE_DELETE` can make writer rename fail and consequently deny pre-effect MCP work. #4 owns the native Windows share/delete and concurrent-rotation proof.
- **Action correlation:** `RequestKey = (server_id, request_id)` identifies a specific MCP call. `EffectKey = (server_id, operation_id)` identifies the newly admitted effect; a retry gets a new request, not a second effect. The effect belongs to its original admitted request even if another chat replays it. `session_id` means a **managed terminal process**, not an AI chat. `request_finish` is not interchangeable with `operation_finish`, and process exit is known only through later recorded observations.
- **Bounded projection vs complete history:** a small `ActivitySummary` exposes source hint/confidence, stable request/effect references, tool, phase/status, ordering/time, replay and unknown flags, and a bounded human-readable command/file hint for discovery/SSE, **not for the owner-visible historical action card**. Authenticated selected-history pages include the **complete persisted original source records within a byte budget**, allowing normal action cards to show full input inline by default. Exceptional deferred records are retrieved in full by a separately requested detail lookup authorized **on every call using the same scoped viewer token** (not a second credential). Use `Cache-Control: no-store` and strict output escaping. A finish whose `request_start` is beyond the loaded window is `origin_not_loaded`, not “unattributed”; #5 handles late-origin reattribution and idempotent replay, while #7 owns bounded historical lookup. In-flight effects from the current server instance are retained until real completion.
- **Snapshot → live:** future authenticated consumers must capture the **Forward frontier cursor before loading Backward history**, then start live delivery after the saved cursor; overlap can replay records but must not silently miss an admitted append. Future history/live APIs expose coverage and resume state. Consumers must not deduplicate by `RecordPos` alone: a page-provided `RecordRef` carries an eventual archive suffix hint stable across normal rotation, but oversized damaged rows have no `Ref`; #5 must define an occurrence identity for all rows from source and ordering context without importing the reader. A hint is a locator, not a tamper-proof identity. On detected invalidation, rebuild from a fresh bounded snapshot and report a gap. Stream delivery does not participate in admission or fail-closed audit decisions.
- **Unavailable data:** audit disabled or damaged is an explicit viewer status, not an empty “complete” history. No inference of actual model, chat title, chat creation/closure, trusted ingress or indirect filesystem mutation. Any live process-state overlay would be clearly *volatile* and is **not** added to the MVP without separate scope.

The four normalized identity field names above are fixed; the remaining contracts are behavioral boundaries. The owning issues select Go types, other wire fields, routing names, cursor encoding and implementation techniques, subject to [#2](https://github.com/dimchansky/terminal-mcp/issues/2).

## 4. Owner entry, security and service lifecycle

**MVP entry:** HTTP-mode server only, using the **existing canonical literal loopback host and port** (normally `127.0.0.1:8090`). Add an explicit `terminal-mcp dashboard` convenience action: for a **standalone `start`** instance, use its existing saved local listener and protected token-file configuration ([controller](../cmd/terminal-mcp/standalone.go#L22-L85), [control](../cmd/terminal-mcp/standalone.go#L380-L425)). An independently launched foreground `serve` instance has no guaranteed discoverable saved config: require an explicit target address and token-file path (or a safely inherited existing token environment) for the CLI action; missing/disconnected service returns a clear error. The stdio transport has no web viewer. No auto-launch or external network exposure is implied.

**Authentication:** the CLI proves ownership using the existing local full-power bearer **outside the browser**, obtains a short-lived, unguessable, single-use *viewer-only* pairing code and opens a **grant-free** local login URL. For the initial MVP, the code can be displayed in the private terminal for manual paste; this friction is intentional until an equally safe flow is demonstrated. **Neither bearer nor pairing code appears in browser argv, URL, referrer or persistent storage.** After exchange, the browser holds a separate **read-only**, expiring viewer token in per-tab `sessionStorage` (page reload keeps it; a new independent tab needs login) and sends it as a header for every history/detail/live request. SSE-format delivery uses authenticated `fetch`, not cookie-only `EventSource`. Viewer credentials never authorize `/mcp`, maintenance or file/process mutation.

**Access boundary:** viewer routes have their own strict exact Host/Origin/Fetch-Metadata and header guard; do not relax `httpguard.Wrap`'s restrictions on `/mcp` and existing admin routes ([guard](../internal/httpguard/guard.go#L69-L105)). A tightly enumerated local-admin pairing operation uses full bearer; access to it over the embedded tunnel must remain impossible. The tunnel currently forwards **only** exact `/mcp` ([source](../cmd/terminal-mcp/tunnel.go#L153-L169)). The transport's existing ability to execute commands/read files means remote agents trusted with the MCP bearer may already read the audit: viewer-route isolation is not a new sandbox or user identity boundary. **A read-only viewer credential is still highly sensitive:** it grants access to complete audit inputs, which may include passwords, tokens, signed URLs and source code. Require a strict CSP without inline/eval or third-party scripts, render untrusted tool text through text nodes (no HTML interpretation), and avoid external assets, telemetry and exposing raw inputs in browser logs. Keep limits on login attempts, grants, viewers, live streams and detail reads.

**Lifetimes and stopping:** choose bounded rolling viewer expiry with a separate absolute maximum. Viewer pairing, login and read-only routes are **independent of the MCP mutation admission gate**; they remain available during draining subject to viewer authorization/resource limits, and are rejected at the final viewer fence. Permit **new pairing and renewal during a long graceful drain**, subject to the same strict authentication and resource caps: read-only viewing is not a new mutation, and the owner may need to open the dashboard specifically to see what is delaying shutdown. One shared shutdown point, immediately **before `httpServer.Shutdown`** in `serveHTTPWithOptions`, must atomically fence new viewer requests, send a best-effort viewer-only `server_stopping` signal, cancel existing viewer handlers and then invoke the existing **unbounded** production HTTP shutdown. On the **normal `ctx.Done` → `Shutdown` path** this point follows the appropriate mode-specific preparations: `TryFinishDrain` for ordinary stop and externally coordinated freeze for update. Force may abort effects and need not await a viewer; **every alternative exit** (including unexpected `Serve` failure or forced close) must either fence/cancel viewers or close their connections directly. Do not claim all effects completed on force. It must cover SIGINT/SIGTERM, maintenance stop/update and force, without allowing viewer handlers to delay MCP. This timing is an approximation of live coverage, **not a promise that every audit event was streamed**: `TryFinishDrain` waits for mutations/sessions but not necessarily every read-only HTTP request, whose `request_finish` may be written during HTTP shutdown and remain available only via replay ([manager](../internal/session/manager.go#L389-L450), [HTTP shutdown](../cmd/terminal-mcp/main.go#L387-L422)). #6 owns the viewer fence/cancel primitive; #8 calls it once at this common shutdown boundary. An operator invoking `terminal-mcp dashboard` during an update freeze may still authenticate against the **old** live instance until the final fence; after activation/restart its viewer tokens are invalid. Show a re-login state, not endless reconnection.

**UX tradeoffs accepted:** one port, one process and a simple CLI-assisted login outweigh automatic new-tab sign-in and surviving service updates without login. Exact TTLs, endpoint paths and session-store implementation belong to #6; they must realize the safety and continuity policy above.

## 5. Desktop UX: conversation history with live updates

**Primary view:** the page is a **history browser for observed MCP actions**, continuously extended by live events — **not** a live-only ticker. Opening the page immediately loads a bounded recent historical snapshot, shows the conversation/source lanes found within that coverage, and selects a recent identifiable lane (or Unattributed if none exists). Selecting another lane shows its own recorded timeline: *what the client requested, when, what outcome was observed and how long the relevant lifecycle phases took*. Older retained history is available on demand. Full AI chat messages and client windows are not visible to this server.

Low-fidelity sketch (all data **fictional**). The selected conversation gets the main screen area. Its primary representation is a **human-readable command, a requested change, or actual submitted file content** — not field names from JSON. ▣/▧ are optional deterministic identicons, not authenticated identities.

```text
MCP ACTIVITY   ● Connected · audit writes healthy      [ ] Auto-switch chats
Sources                    Build work · claimed OpenAI 7fa2… · history
▣ Build work                11:15:18  Process launched · terminal_start
▧ Deploy · 3 new                Working directory: /Users/demo/project
◇ Unattributed · 1 new          $ GOFLAGS=-count=1 go test -race ./...
                                 Request 38ms · launch 15ms
                                 Process runtime not observed
                                 [Original JSONL] [Receipt if recorded]

                           11:17:03  File edit applied · internal/service.go
                                 Requested replacement #1:
                                 - timeout := 5 * time.Second
                                 + timeout := 10 * time.Second
                                 Request 43ms · operation 24ms
                                 [Original JSONL]

                           11:19:40  File write applied · internal/config.go
                                 package config

                                 const TimeoutSeconds = 10
                                 [Original JSONL]

[Discover older conversations] [Earlier in this conversation] [Jump to latest]
```

**Human-readable presentation is the default, forensic source is always available:**

- **Process launch:** show **one readable command line with all supplied environment overrides placed before the executable and arguments**, with the working directory plainly visible. On Unix-like systems render a faithfully POSIX-shell-quoted *display equivalent* such as `GOFLAGS=-count=1 go test -race ./...` (quote spaces, quotes, dollars and other special characters correctly). This represents the direct `argv`/`env` invocation for human inspection; it **does not assert that the server ran a shell**. If an argument is itself a shell script (`sh -c`, `zsh -lc`, etc.), show that supplied script readably while retaining the real interpreter invocation. On Windows, render a deliberately labelled platform-appropriate form, not a fabricated POSIX command. If faithful command notation is impossible or ambiguous, fall back to visibly labelled individual arguments/env values with a warning — never silently change their meaning. Exact `argv`, `cwd`, env and options remain available in the original JSONL. A copyable command is offered only when its quoting/encoding is correct for the labelled shell.
- **Requested file edits:** show the **filename and visual diff** for *every* `old_text` → `new_text` replacement, with removed text visually distinct from added text, including multiline edits. This is a comparison of what was **requested**, **not** a guaranteed diff of the resulting on-disk file. Do not elide unchanged lines inside supplied old/new text, hide later replacements, drop edit flags or guess line numbers; show exact complete before/after strings and remaining supplied parameters. If a faithful diff cannot be produced, show full old and new text side by side or in clearly labelled blocks.
- **File writes:** show the actual supplied `content` as a readable, monospaced text/code block under the path, not the literal label `content:` followed by a JSON field listing. Include all original lines. Other tools use similarly human-oriented labels and layouts; raw field/property notation is a **fallback**, not the standard presentation.

**Input-first cards (owner's actual audit, not a reduced telemetry dashboard):**

- Every ordinary-sized action card automatically shows the **actual full recorded input in a human-readable form**: a quoted, environment-prefixed command for `terminal_start`; a complete visual requested-replacement diff for `file_edit`; complete source text for `file_write`; readable exact input text/keys/bytes for `terminal_write`; and recognizable paths, URLs and options for the other tools. **No raw `argv[0]`, `edits[0].old_text` or similar JSON-schema field listings as the normal main view.** Additional supplied flags/options must remain visible, while status/duration stay secondary.
- Human-readable formatting never acts as a whitelist: **all supplied unknown/nested/extra fields** appear in an inline *Other supplied fields* section. If the input has an unexpected shape, contains ambiguous/unsafe characters, or failed schema validation, use a complete generic source display instead of a misleading command or diff. Specialized views must be deterministic and preserve all model-supplied values. Also expose recorded `call_meta`, `input_responses` and `request_state` if present. Never invent returned file bodies, process stdout/stderr, full command runtimes or fields the audit did not record. A replay shows **its own supplied args** and links to the original effect; it must not display original args as though they were resubmitted.
- The *Original audit JSONL* view/copy action reveals the **entire persisted source record text**, not a JSON object serialized again by browser `JSON.parse`. Original *recorded values*, including large integers, duplicated keys, escaped characters and unexpected fields, must remain recoverable. If a friendly view would lose or misrepresent such values (e.g., duplicate keys, unsafe JavaScript numbers, lone surrogates), show a visible ambiguity warning and use the source-text view. Render terminal control bytes, ANSI sequences, NUL, carriage returns, bidirectional and zero-width Unicode visibly/escaped **for display** without altering the original copyable value. Do not present an argv array as though an actual shell executed a reconstituted command line.
- **Honest absence:** if `request_start` lies outside the loaded window, show `origin_not_loaded` and offer bounded lookup. If the logger emitted only `request_rejected` because an input could not be fully recorded (oversize/unrepresentable), show **“Input not recorded — tool not executed”** and the actual reason: there is no original input available to expand. Show errors/statuses and `operation_finish.receipt` **only when actually present**; a server-truncated error must be marked truncated. No masking or censoring of complete model-supplied inputs, including secrets, signed URLs or private file content.
- **Efficient delivery without reducing content:** history pages (#7) include **complete source records** within a bounded *total byte budget*, so typical visible cards already contain their actual input without one HTTP detail request per card. An exceptional near-4-MiB record exceeding the page budget is explicitly marked `deferred` with exact size and an authenticated in-card **Load complete original** action. This retrieves the **entire single record**; render it in a scrollable fixed-height block, never permanently replace it with a truncated preview. Pages must advance their cursor even over a deferred record. SSE (#8) stays compact (references/cursors only); the UI hydrates live cards via **batched history reads**, not N+1 single-card fetches or massive SSE broadcasts. Virtualize offscreen cards, keep scroll position stable and keep full private data only in memory (never browser persistence/telemetry). No separate chunking protocol, database or code-editor framework is required for supported audit records (up to about 4 MiB).
- Every source-record view is owner-authorized and `no-store`; no third-party scripts or external assets. All content renders as inert text with safe escaping and a strict CSP. Full raw input is deliberately visible to the authenticated owner; this includes sensitive material, so the page is not suitable for casual screen sharing. The complete raw forensic journal remains unchanged.

**History navigation and discovery:**

- Two distinct actions: **Discover older conversations** extends the **global scan coverage** backward, so previously unseen source lanes can appear; **Earlier in this conversation** fetches older matching actions for the selected exact `(identitySource, conversationId)` hint. The Unattributed view is a filter, **not** a fictional conversation. A single **bounded backward scan** primitive (owned by #7; based on #4's safe reader) can serve global discovery, filtered source history and origin lookup with different predicates. It returns scan coverage and a continuation even if a page contains **zero matching actions**. Do not require a new database/index or scan all unbounded archives at once.
- Display the **scanned** time/record range and the known retained-history boundary; never claim all conversations are discovered while earlier records remain unscanned. Missing/changed archive or invalid cursor gives an explicit gap/resync. A stable client-claimed hint may group requests across server restarts but does not prove distinct chat identities. Source aliases, short labels and identicons aid recognition without replacing full original identity fields in the API.
- Within a lane, show **correlated actions with complete recorded input inline by default**, not just a name/status row plus an optional Details panel. The full source-record view remains accessible for each action and large deferred records can be loaded into the same card. The list follows **journal append order**; timestamps are shown in browser-local time (UTC available on inspection). A tool call made in lane B that inspects a managed process started in A remains an action **in B**, with a link to A's original process/effect; replay in B must not duplicate A's effect. An old finish with no loaded origin remains `origin_not_loaded` in a visible global pending-origin indicator until resolved, not misclassified as Unattributed.

**Time and duration honesty:**

- `request_finish.duration_ms` measures the MCP **request** including audit overhead and any tool wait/poll interval; `operation_finish.duration_ms` measures the admitted **operation lifecycle**, not necessarily a terminal child's runtime. In `terminal_start`, the recorded effect is **process launch**, not shell command completion. Do not infer runtime from two wall-clock timestamps.
- Because `duration_ms` has `omitempty`, a current-schema finish with the matching start and no duration field means **less than 1ms**; a legacy/incomplete record without adequate start/finish evidence means **unknown**. The model distinguishes measured, sub-millisecond and unknown durations rather than inventing zero or displaying an unqualified “duration.” A terminal process without observed completion explicitly shows **runtime not recorded**.

**Switching and attention:**

- Manual chat selection is the default. **No Pause control**: incoming events continue to update history regardless of the selected lane or whether the browser page is open. With auto-switch off, activity in an inactive lane leaves focus unchanged and raises a **new activity indicator/count** (a small coloured dot is fine, with accessible text/count and distinct styling from audit health or success). New activity in the selected lane may be unread when its tab is hidden or the timeline is scrolled away from the live tail.
- **[ ] Auto-switch chats** (optional, initially off; persist the non-secret preference locally) changes **attention only**, never the audit or stream subscription. A new, **live** non-polling `request_start` from another *identifiable* lane can select it. Do **not** focus-switch on initial snapshot history, earlier pages, late backfill, duplicated stream delivery, `request_finish`, `operation_finish`, repetitive `terminal_read` / download-result polls, or Unattributed calls. Other meaningful state changes still appear in that lane and may become unread.
- Avoid thrashing: after **manual or automatic** selection, keep a short focus-hold interval (about five seconds; exact UI tuning owned by #9). During rapid interleaving, retain current focus and show indicators on other lanes rather than queueing stale switches. If the owner is reading older history, an expanded detail or selected text, **defer** auto-switch while leaving the checkbox on and show pending activity; returning to the live tail restores eligibility. Do not snap historical scrolling to the bottom: show `Jump to latest` for the selected lane.
- Count **unviewed logical action rows**, including a collapsed polling group, **not raw audit phases**. A start plus finish of one action received while unseen counts once; a status change on an already-read row makes it unread again once. Deduplicate by source/action/record identity **before** counting; late origin backfill or replayed network deliveries do not create fresh activity. Selected-lane actions are marked seen only when the page is visible and the newest row is actually in view. Unread is ephemeral **per-tab presentation state**: historical snapshot and reload start at zero; reconnect replay cannot inflate it. Clear only the viewed lane, not other lanes.
- #9 should define and test a small fixed class table for **mutation, process launch, read, polling**: which live starts may auto-switch, which updates count as unread and which polls are collapsed. Raw audited input remains accessible and unmodified; a compact/possibly truncated activity summary is labelled as such. States for live/reconnecting/coverage gap/audit disabled/draining/unauthenticated/expired remain visible.

**MVP:** per-lane history **with actual full model-supplied commands, edits and content rendered human-readably inline (environment-prefixed commands, visual requested-edit diffs and code/text blocks)**, truthful timestamps/request-effect elapsed times, bounded older-history navigation, live continuation, manual selection, optional auto-switch and new-activity markers, exact raw source-record access and owner-only authentication. **Defer:** full AI transcripts/names/models, complete process stdout, unobserved filesystem diffs, global full-text search/analytics, remote dashboard and decorative styling.
